## 四、行为探针暴露的新问题（2026-09-25 晚补记）

### P14 循环内检索延迟未为 agent 调用模式优化（新，高优先）
- **实测**：行为探针每题 ~15 分钟；LLM 步进本身 p50 1s（服务器空闲），
  慢在每次 search_papers 都跑**完整管线**（A3 意图理解 5s + 3-4 子查询 ×
  语义层 2-3s + 关键词层 2-12s + 重排 1s ≈ 30-60s/次），而 agent 循环
  每题调 5-12 次
- **为什么是设计错配**：A3 意图理解是为"用户原始问题"设计的（自然语言
  →关键词分解），但 agent 循环里的查询已经是模型精炼过的关键词——
  再跑一次 A3 是纯浪费。重排对每轮的新查询也不可省但可以快
- **修法**（两条，SQA2 前做）：
  ① broker 的 search_papers 调用走 fast 档/新增 agent 档：
     跳过 A3（查询已精炼）→ 直接语义层单发 → 只在结果薄时才展开多子查询
  ② 子查询层内并行（见 P15）
- 预期效果：单次外部调用 30-60s → 5-10s

### P15 检索层内并行缺失（新，与 P14 配套）
- **现状**：discover_tiered 是严格串行 tier 链（语义层→关键词层逐个降级），
  SearchService._full 的多子查询也是串行 for 循环。唯一的线程池只是
  超时保护（max_workers=2）
- **Sciverse 限流实测**：8 连发（0.5s 间隔）零失败；A6 run2 里 108 题
  连续几百次调用才在 q80 左右偶发一次限流——**并行 3-4 路完全安全**，
  熔断器本来就是为偶发限流准备的
- **修法**：①多子查询并行执行（ThreadPool 3-4 workers，各自走 tier 链，
  结果合并后统一重排）②关键词兜底层与语义层并行发起而非等语义层
  失败才动（浪费的时间是串行链的主要来源）。注意与 P14 的顺序：先 P14
  （跳过无谓的 A3）收益更大且零风险，P15 的并行要配合熔断阈值重新
  校准（并行=突发流量，可能提前触发限流）
