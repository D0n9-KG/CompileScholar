## 拆解（为什么降）

novel 边本身只占 8/229，其 both-pass 1/8——**拉低总量约 1.3pt**，不足以解释 5.4pt 降幅。剩余降幅来源：
1. **单 run 方差**（前科 37% 边数波动）——5.4pt 在方差带内，两臂各自都是单 run
2. 内层 judge（Claude）给 B 臂 67.2%——与 API judge 的 28.4% 差异巨大，两 judge 体系的口径差未校准
3. 新 pattern 进入 meta 后**改变了后续抽取的行为**（schema 变大→检索/compact 路径变化→边分布变化）——间接效应方向不明

## 诚实判定

- **预注册主门柱未过**：不支持"改道提升语义质量"的强主张
- **但三个次级信号正向**：召回+16 边、novel 边质量 62.5%（内层口径）未拖后腿、divergence 被治理闸压住（2-3/篇 vs A6 前科 38/篇）
- **单 run 双 judge 无法分辨 5.4pt 是真降还是方差**——判决需要多 seed，这本来就是预注册里"正式数字多 seed"的要求

## 按预注册预案处置

DECISION 的失败预案："B 的 both-pass 反降 → 回滚改动 ①（保改动 ③ 的归纳通道吃 dropped 边）"。

但预案写时没料到降幅在方差带内+novel 边本身不差。**修订建议（需用户确认）**：
- 不完全回滚——改动 ②（kernel 豁免）+③（归纳通道）无害且次级信号正向，保留
- 改动 ①（gate 放行 novel 边）**降级为可开关**（env SOFT_ROUTING=0/1），多 seed 时两态都跑——让它成为被测变量而不是既成事实
- 判决推迟到多 seed（这是预注册"正式数字多 seed"的本来要求，单 run 判 5.4pt 本就不科学）

## 与内层 judge 的校准差（重要方法学数据）

Claude 内层 67.2% vs API both-pass 28.4%——**差 39pt**。两体系对同一批边的判定天差地别（内层判 PASS 的 154 条里 API 只认 65）。这个差距本身要仲裁：抽 20 条内层-PASS-但-API-FAIL 的边终裁，确定哪个口径更接近真相。若内层偏真，API both-pass 作为门柱口径要重议。
