# Phase 3-4: Extraction Noise Filtering & Quality Gates Design

> **Date:** 2026-02-16
> **Status:** Approved
> **Prerequisites:** Phase 1-2 (P0-1~P0-4) complete

## Executive Summary

**Goal:** Improve evolution quality from current state (16 edges, unknown coverage) to production-ready (≥20% coverage, <5% self-loops).

**Approach:**
- **P0-5:** Filter extraction noise at source (figure captions, pure definitions)
- **P0-6:** Add hard validation gates to enforce minimum quality standards

**Expected Outcome:**
- Evolution coverage: 0.56% → ≥20%
- Data quality: High noise → Clean, meaningful relations
- Reliability: Silent failures → Explicit quality gates

## Problem Statement

### Current State (After Phase 1-2)

✅ **Fixed:**
- Mode tracking working (lexical fallback)
- Mode-aware thresholds (0.70 for lexical, 0.85 for embedding)
- Self-loop prevention (text identity → MERGE events filtered)
- 0 edges → 16 SUPPORTS edges

❌ **Remaining Issues:**

**Issue 1: Extraction Noise (P0-5)**
- Claims contain figure captions: "Figure 1: Experimental setup"
- Claims contain pure definitions: "Machine learning is a method of..."
- Noise dilutes evolution signal, creates meaningless relations
- Previous test: 0.56% coverage due to noise pollution

**Issue 2: No Quality Assurance (P0-6)**
- Evolution rebuild can produce terrible results but show "succeeded"
- Examples: <5% coverage, >20% self-loops still marked as success
- Silent failures waste resources, hard to debug
- Before fixes: 1456 events but 0 edges, task still "succeeded"

## Design Decisions

### Decision 1: Where to Filter Noise (P0-5)

**Options Evaluated:**

| Stage | Pros | Cons | Decision |
|-------|------|------|----------|
| **Extraction** | Stops noise at source, benefits all downstream, cleaner graph | Requires data rebuild | ✅ **SELECTED** |
| Similarity | Quick patch for existing data | Noise still in graph, wasteful computation | ❌ |
| Evolution | Minimal code change | Too late, metrics polluted, worst quality | ❌ |

**Rationale:** Extraction-stage filtering provides best long-term data quality. Short-term rebuild cost is acceptable for 20-paper test dataset.

### Decision 2: Where to Validate Quality (P0-6)

**Options Evaluated:**

| Approach | Pros | Cons | Decision |
|----------|------|------|----------|
| **Before Neo4j write** | Transactional safety, clean failure, easy to test | None | ✅ **SELECTED** |
| After Neo4j write | Can inspect "what would be written" | Complex rollback, partial state risk | ❌ |

**Rationale:** Validate-before-write aligns with "fail fast" principle, provides transactional safety.

## Quality Metrics Definition

### Coverage Rate

```
coverage_rate = covered_propositions / total_propositions

where:
  - total_propositions = count from sync_proposition_mentions_global()
  - covered_propositions = unique propositions in accepted edges (SUPPORTS/CHALLENGES/SUPERSEDES)
```

**Threshold:** ≥ 20%

**Rationale:** Below 20% suggests insufficient relations or excessive noise.

### Self-Loop Rate

```
self_loop_rate = self_loop_accepted_events / total_accepted_events

where:
  - self_loop_accepted_events = events where source_prop_id == target_prop_id AND status == "accepted"
  - total_accepted_events = all events where status == "accepted" (excluding mention events)
```

**Threshold:** < 5%

**Rationale:** Self-loops indicate bugs in filtering or mapping. Should be rare.

## Error Handling

### P0-5: Graceful Degradation

**Scenario:** Noise filtering function fails

**Behavior:**
```python
try:
    filtered_claims, stats = filter_claim_candidates(claims, rules)
except Exception as e:
    log(f"Noise filtering failed: {e}, proceeding without filtering")
    filtered_claims = claims  # Fall back to unfiltered
    stats = {"error": str(e)}
```

**Rationale:** Backward compatible, doesn't break existing pipelines.

### P0-6: Hard Failure

**Scenario:** Quality gates not met

**Behavior:**
```python
if metrics["coverage_rate"] < settings.evolution_min_coverage:
    raise ValueError(
        f"Evolution coverage too low: {metrics['coverage_rate']:.2%} "
        f"(minimum: {settings.evolution_min_coverage:.2%})"
    )
```

**Outcome:** Task manager marks task as FAILED, user sees clear error message.

**Rationale:** Explicit failure better than silent bad data.

## Risks & Mitigation

| Risk | Impact | Mitigation |
|------|--------|------------|
| P0-5 over-filters valid claims | Data loss | Start with conservative rules, monitor filter stats |
| P0-6 gates too strict | Excessive failures | Make thresholds configurable, can disable if needed |
| Data rebuild time | Implementation delay | Only 20 papers, acceptable delay |
| Backward compatibility | Break existing workflows | Add enable/disable flags, graceful degradation |

## Appendix: Noise Filter Heuristics

### Figure Caption Patterns

```
- "Figure \d+:"
- "Table \d+:"
- "Fig\. \d+:"
- Starts with pattern, low semantic content
```

### Pure Definition Patterns

```
- "X is a Y"
- "X refers to Y"
- "X is defined as Y"
- High is/are density, low verb diversity
```

These are starting heuristics; can be refined based on test results.
