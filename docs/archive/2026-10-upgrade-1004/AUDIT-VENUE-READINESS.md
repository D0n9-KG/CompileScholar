## 0. 结论先行

1. **按现状投四个目标会场，都会被拒。** 问题不在写作，在主张和证据对不上。论文主张"领域状态让 agent 答得更好"，
   唯一直接测这件事的消融（CS2 去状态通道）结果是 Δ=+0.000 [−0.037,+0.034]。答题库里的"状态"其实是综述目录的搬运
   （field_state.py:4-5 自己写着：842 条状态证据中 841 条与 KB 已有记录逐字相同）。真正的领域状态编译器只在留出检验里跑过，没进答题库。
2. **CS2 上比 harness 高的 +0.094，很可能主要来自引用格式，而不是知识组织。** 长度对齐后，增益全部在引用两项（CR +0.40 / CP +0.11），
   IR 打平。实测（dev 同 15 题）：我们每条引用附带的片段中位 1,102 字符（基本是整段摘要），每个答案 32 条引用；
   harness 中位 234 字符、15 条。判分器拿到的可核对证据量差了 4–5 倍。没有格式对齐的对照，审稿人会直接这样解读。
3. **留出综述检验目前最像"状态有用"的证据，但有三处一定会被抓。**
   - 在 14/18 篇综述上，state 和 state_v2 是同一份代码、同一批记录跑的两次随机运行。草稿把它们当两个系统，每列挑较好的那个加粗。
   - 两次运行之间的差距（族召回 +0.088 [+0.027,+0.157]）和声称的效应一样大。
   - 判分只看前 250 条候选，而 flat 臂的性质候选在 14/18 篇上超过 250 条（中位 396，最多 1,185）。
   两次运行取平均后：族 state−direct +0.121 [+0.007,+0.240]，族级性质 +0.035 [+0.007,+0.073]，局限 +0.050（不显著）。
   效应还在，但更小，也更脆。
4. **另外两个基准是持平或负面。** Multi-108 严格口径 0.424，和 LightRAG 0.461、PaperQA2 0.431 打平，低于旧系统 0.532。
   DSB 0.310 和旧 harness 0.299 打平，比 oracle 直写低 0.059。检索是瓶颈（失分的 60.6%），我们没解决。
5. **目前最站得住的是两样副产品。**
   - 评测效度发现：长度混杂、截止泄漏 42/93、适配器口径（GPTR 0.763→0.557，Elicit 0.714→0.798）、Multi 指标定义翻转、Multi-108 有 10 题数据错配。
   - 逐句证据引用写作带来的 CS2 引用质量提升。这一条要等格式对齐对照做完才能说。
6. **上顶会需要一个决定性实验。** 要在一个"答案必须跨论文聚合"、而且没被碰过的题集上，同管线、同写作器、同检索预算，
   比较"记录+编译状态"、"只有记录"、"查询时现场编译状态"三种设置，主假设和统计功效都事前定好（§3a D1）。
   做出正结果就是方法论文；做不出来就转 D&B 或分析论文（§3d）。
7. **草稿里的功效分析写错了。** §7.2 用配对 SD≈0.24 推出"检出 Δ=0.05 需要 176 题"。按当前管线在 dev 上实测，配对 SD 是 0.093（v9b−harness）
   和 0.071（去状态消融）。100 题 test 的最小可检出差约 0.026（80% 功效，α=0.05 双侧）。好的一面是 test 够用；
   反过来，"test 太小、检不出小差异"这个辩护也不能再用了。

外加一个小留出检验"，核心组件对胜利的贡献是零。要翻盘需要三样东西：D1 正结果、D2 规模曲线、成本表。还要正面回应
"为什么不直接用 ScholarStack/LKM 式的大规模编译"。WWW 不再是时间约束（用户 10-04 裁定），所以不必为它赶工。

**SIGIR。** 这里最看重评测严谨性和检索贡献。我们自己的数据显示检索是瓶颈：DSB 失分 60.6% 在检索层，开放检索下金标参考文献重合
5/55。可草稿 related work 写的是"引文扩展不是我们的贡献"。有一条 SIGIR 能接受的叙事路线：review_1002 p8 实测，
引文频次和语义合并的候选池，召回@100 是 0.423，纯语义是 0.209。这是 IR 贡献，前提是要有合规、可复现的引用图数据源（§3d 方案 C）。
按现在的叙事投 SIGIR 必拒。

**ACL/EMNLP（ARR）。** 审稿人会盯三件事：LLM-as-judge 的效度、有没有人工评测、分析做得深不深。Soundness 2.5 的理由是主张超出证据；
Excitement 2 的理由是叙事档 §2 自己承认"组件都有先例"。要翻盘需要 D1、人工一致性检验、第二个 backbone。
如果翻不了，把评测效度分析写扎实，Findings 是现实上限。

**NeurIPS D&B。** 如果把留出综述重建做成正式基准（暂称 FieldBench），D&B 是最对口的会场。但要满足这些：100 篇以上综述、多领域、
金标经人工核验、datasheet 和 Croissant 元数据、许可分析、托管与维护计划，还要跑一组强基线（AutoSurvey、SurveyForge、长上下文直写、
TaxoBench 协议）。现状是 18 篇综述；金标 `text` 字段是早期 LLM 抽取的改写，不是作者原句（build_survey_gold.py:55,57）；
族名里混着单个方法名（例如 2403.14734 的族金标里有 "CODE-MVP"）。评测效度审计这部分和 D&B 的口味最搭，可以并入。

## 3. 上顶会必须做的升级

### 3a. 系统和方法升级

**S1 答题库的状态层换成真编译，和留出检验共用同一个编译器。**
- 用 `field_state.compile_field_state` 按领域簇编译（arXiv 主类加嵌入聚类，每簇 50–300 篇），输入是原始论文记录，不再搬综述目录。
- 产物：族、族级性质、族级局限、领域问题，每条都带逐字 support。
- 冻结哈希后替换 `state_merged.json`，接到 `KB.state_search`（answer_pipeline.py:79-114）。
- 验收：每条族级事实都能解析到库内论文；报 n_papers≥2 的占比；做人工忠实度审计（D4）。
- 综述 taxonomy 不扔，作为一个单独的来源（"综述作者的划分"），和编译出的族并列，在消融里分开测。

**S2 跨论文边解析到论文。**
- 谱系边两端现在是名字字符串，严格解析 0/2422。
- 做法：用 refgraph 取参考文献表，按"作者 + 年份"对齐，再从每篇论文抽"本文提出的方法名"，把方法名解析到提出它的论文。
- 验收：解析率；人工核 100 条边，精度目标 ≥0.85。
- 这条是 D1 里"演化类"问题的前提。

**S3 族内立场：共识、限定、争议。**
- 对同一族内的事实做 support / qualify / refute 分类。标签体系对齐 ClaimFlow（2603.16073），用它 1,617 篇的人工标注做分类器验证集，
  这样不用另建金标。
- 由此派生每条族级事实的状态：共识（≥2 篇独立支持、没有反驳）、有条件、有争议、单一来源。
- 这是"状态"区别于"聚类加摘要"、而且可以检验的部分，也是与 ScholarStack（原文 "does not model field consensus"）划界的唯一硬点。

**S4 答题时结构化地使用状态，而不是把它当第四路检索。**
- 现在状态证据只是带个 `[property of 'X']` 前缀混进证据表（answer_pipeline.py:110），写作器并不知道它处理的是族级对象。
- 改法一：按题型路由。领域级问题（"有哪些方法、差别在哪、共同局限是什么"）先取命中的族，按族来规划小节；
  具体问题不走状态通道，避免伤到 AP。
- 改法二：写作规则要求族级共同局限和共识这类句子必须多引用，并标出 n_papers。
- 片段只放原文，族和角色信息放进 citation metadata，不再写进 snippet，否则"可核对"的说法不成立（§3d）。

**S5 方差控制。**
- plan、screen、write 的温度全部可配，默认 0。现在 write 是 0.2（answer_pipeline.py:510），plan 失败时重试用 0.3（:344）。
- 外部检索响应按题落盘，冻结，可以离线回放（§3c C3）。
- 每臂至少跑 3 次。

**S6 "生长"：要么给出可度量的结果，要么从方法章删掉。**
- 方法章 §3.4 描述了生长，但现在没有任何生长结果；旧的 marathon 只解决了 1/24。
- 如果保留，至少要有：每轮新增论文数、引文前沿命中率，以及冻结后对 D1 主指标的影响。否则在论文里只算未来工作。

### 决定性实验（证明状态层重要的唯一途径）

**D1 FieldQA：领域级问答上的状态消融（主实验，预注册）。**
- 题集：从没进过 KB、也没被开发看过的留出综述里，按四类模板出题：
  - 方法族和它们的区别；
  - 某族的共同局限；
  - 本领域的开放问题；
  - 某方法的演化与替代关系。
- 金标：综述作者原文的陈述，人工确认能从被引论文推出（只保留可答的）。
- 规模：≥150 题、≥40 篇综述、≥5 个 arXiv 类别。功效按实测配对 SD≈0.08 算，最小可检出差约 0.018。
- 对比臂：同一管线、同一写作器、同一检索预算、同一 27B。
  - **Full**：记录 + 编译状态（S1/S3/S4）。
  - **−state**：只有记录。
  - **Query-time compile**：答题时对检索到的论文现场跑 compile_field_state。用来测"预编译"本身有没有价值，这是审稿人一定会问的。
  - **−KB**：只开放检索。
  - **Oracle-state**：用综述自己的 taxonomy 作状态，作上界。
  - 外部系统：OpenScholar、PaperQA2、STORM、AutoSurvey。
- 主指标：rubric 式 ingredient recall（CS2 同款 judge，加人工核验），配 AP，再加"族级判断准确率"。
- 主假设 H1：Full − (−state) > 0。单侧 α=0.05，配对 bootstrap，n≥150，3 次运行取均值。
- 次假设：Full − QTC > 0（预编译的价值）；Full 在 CS2 上对 −state 非劣（界 −0.02）。
- 预案：H1 不成立就走 §3d 方案 B，不再加题、不换指标。

**D2 规模曲线（回答"为什么要预编译"）。**
- 同一个领域，论文数取 30 / 100 / 300 / 1000 四档，往里加同类干扰论文。对比 state、direct（长上下文直写）、QTC。
- 假设：direct 在 300 篇以上因为上下文装不下而下降，state 保持稳定；QTC 的单题成本随规模线性涨。
- 同时报编译的摊销成本：编译 GPU 小时除以复用题数。叙事档 §3.3 计划了规模三档，至今没做。

**D3 CS2 内的机制检验（不加题，提高功效）。**
- 把 CS2 rubric ingredient 按类型分层：局限/挑战 18–19%、比较 25–33%、演化 6–14%、分类约 5%（review-1002 #44 实测）。
- 检验"状态只在这几类 ingredient 上提高召回"：交互项，题级 cluster bootstrap。
- 如果状态有用、只是被总分稀释，这里应该能看到。如果分层后也是零，R1 坐实。

**D4 状态忠实度的人工审计。**
- 抽 200 条族级事实，判三件事：被所引 quote 支持 / 是泛化过度 / 不支持；它是不是真的跨论文。
- 抽 100 条族成员归属，判对不对。
- 没有这一步，"每条都带逐字证据"只说明格式对，不说明内容对。

**D5 去记忆。**
- 留出综述改用 27B 训练截止之后发表的（被引论文可以更早），memory 臂照样保留。
- 现在的 18 篇是 2020–2024 年的，memory 臂族召回 0.317，说明模型记住了不少。

### 3b. 评测严谨性

- **B1 judge 效度。**
  - 用官方 judge（`google/gemini-3-flash-preview`，astabench task.py:406）把全部 CS2 臂全量重判，存档臂也包括在内。

  - CS2 test 抽 60 题，2 名标注者判两件事：ingredient 是否覆盖；每个 citation group 是否被片段支持。报 Krippendorff α，以及 judge 与人工的 κ。
